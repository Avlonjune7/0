# 0-build

## 1. 开工前

- 按 `AGENTS.md` 的指针读取约定、关联规格和实现，互不依赖的读取并行发出。UI 改动先读根 `DESIGN.md`；修改 `DESIGN.md` 本身需要用户同意。
- 复杂任务的规格仍是 `草案` 时，先请用户确认，或回到 0-plan 完成批准。明确的聊天需求可直接实施。
- **读够标准**：能写出"入口 → 改动点 → 受影响调用方 → 验证命令"再动手；有一环写不出就继续读，不靠猜。
- 从规格取 AC 编号；没有规格时先列出可观察的验收结果。
- 记录开工时的提交和 `git status`，用于区分既有改动。
- 会改变业务行为、范围或验收的未决点：保留现有行为，先做明确且独立的部分，再提出具体问题。

## 2. 实施

- 多环节需求先打通一条真实路径，再补边界。正式交付接入实际接口和数据；原型、测试替身和占位要标明，交付时说明未接通的部分。
- 改接口或数据时，验证旧调用方、历史数据，以及规格要求的迁移和失败恢复。
- 适合时按 AC 逐条先写失败的行为测试，再实现到通过。
- **排错**：先用真实入口复现原症状的最小场景；原因不明时，做能区分候选原因的观察或实验；性能问题在相同条件下前后测量。无法复现时记录已有证据和缺失的环境或输入。修复后复测原场景，删除临时排查代码。
- **环境**：复用已在运行的服务、已装依赖和现有工作区。终止进程、丢弃或覆盖未提交改动、重置数据之前，先确认对象由本会话创建或已获授权。

## 3. 验证

- 用项目已有命令验证 AC 和相关回归，按 AC 编号记录结果。多条互不干扰的命令可用 [run_checks.py](scripts/run_checks.py) 并发执行（`--help` 查看参数）。
- 先覆盖本次改动；出现失败或新影响再扩大范围。区分本次引入的失败、已有失败和环境受阻。
- 新增测试只针对现有验证漏掉的具体风险，或满足项目要求。

## 4. 金鱼代码评审

满足任一条件即执行：跨模块、改外部契约或数据、改动约超过 100 行、规格要求、用户要求。纯文案、配置值和单点小修跳过。

1. 派一个无会话历史的只读子代理（Codex 下用 `fork_turns: "none"`），只给比较基线（开工时的提交）、改动清单（可用 [collect_changes.py](../0-review/scripts/collect_changes.py)）、规格或原始需求原文、验证命令。给路径，不贴全文。
2. 要求它沿两个轴各给最多 5 条发现，每条附位置、触发条件和影响：
   - **规格**：每个 AC 是否实现，有无超出授权的改动。
   - **规范**：项目约定、错误处理、兼容和回归风险。
3. 主会话核实后，修复证据成立且无需新决定的问题并定向复测，其余列为待决定。默认只做一轮。

完整规则见 [0-review](../0-review/SKILL.md)。无法派出子代理时，说明未做独立评审。

## 5. 同步与交付

- 同步本次影响的 README、模块说明和运行指引。规格只按已认可的行为更新，与实现冲突时记录差异和依据。已有任务记录更新状态和验证证据。
- 本次新做的关键决定追加到决策日志。
- 交付不超过 10 行：

  ```text
  结果：改了什么、在哪里
  验证：AC-1 通过（命令）/ AC-2 失败（原因）
  评审：金鱼评审 N 条，已修 X 条，待决定 Y 条（或：已跳过及原因）
  缺口：未验证项及原因
  ```

- 发现值得写进 `AGENTS.md` 的教训（反复踩的坑、缺失的命令）时，在末尾提 1 条建议，不自动写入。
- 提交、推送、部署和外部任务状态变更按本次授权执行。
