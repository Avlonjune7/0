# 0-build

## 1. 开工前

- 按项目 `AGENTS.md` / `CLAUDE.md` 指针读取已有 `docs/workflow.md`、关联规格和实现。
- 复杂任务的规格仍是 `草案` 时，先请用户确认或回到 `0-plan` 批准；明确的聊天需求可直接实施。
- **读够标准**：能写出"入口 → 改动点 → 受影响调用方 → 验证命令"再动手；缺一环就继续读，不靠猜。
- 从规格取 AC 编号；无规格时先列出可观察的验收结果。
- 记录开工时的提交和 `git status` 以区分既有改动。若开工时已有脏文件且本次修改同一文件，动刀前保存该文件当时的暂存与未暂存差异，评审时一并交给金鱼作行级基线。
- 会改变业务行为、范围或验收的未决点：保留现有行为，先做明确且独立的部分，再提出具体问题。

## 2. 实施

- 多环节需求先打通一条真实路径再补边界。正式交付接入真实接口和数据；原型、替身和占位须标明未接通部分。
- 适合时按 AC 逐条先写失败的行为测试，再实现到通过。
- **排错**：用最小真实场景复现原症状，无法复现时记录已有证据与缺失条件；修复后复测原场景并删除临时排查代码。

## 3. 验证

- 用项目已有命令验证 AC 和相关回归，按 AC 编号记录结果；多条互不干扰的命令可用 [run_checks.py](scripts/run_checks.py) 并发执行（`--help` 查看参数）。
- 先覆盖本次改动，失败或有新影响再扩大范围；区分本次引入、已有失败和环境受阻。

## 4. 金鱼代码评审

- **触发优先级**：用户明确要求必做；否则满足跨模块、改外部契约/数据、改动约超 100 行或规格要求时执行；纯文案、配置值和单点小修默认跳过。
- 按 [0-review](../0-review/SKILL.md) 的代码评审协议执行一轮金鱼评审：只传开工基线（含同文件脏基线差异）、改动清单（可用 [collect_changes.py](../0-review/scripts/collect_changes.py)）、规格或原始需求原文与验证命令。
- 主会话核实后，修复证据成立且无需新决定的问题并定向复测，其余列为待决定；若本轮存在 [严重] 问题且修复改动较大，对修复部分追加一轮定向金鱼复查；无法派出子代理时说明未做独立评审。

## 5. 同步与交付

- 同步本次影响的 README、模块说明和运行指引。规格只按已认可的行为更新，与实现冲突时记录差异和依据。已有任务记录更新状态和验证证据。
- 本次新做的关键决定追加到决策日志。
- 交付不超过 10 行：

  ```text
  结果：改了什么、在哪里
  验证：AC-1 通过（命令）/ AC-2 失败（原因）
  评审：金鱼评审 N 条，已修 X 条，待决定 Y 条（或：已跳过及原因）
  缺口：未验证项及原因
  ```

- 发现值得写进 `AGENTS.md` 的教训（反复踩的坑、缺失的命令）时，在末尾提 1 条建议，不自动写入。
- 提交、推送、部署和外部任务状态变更按本次授权执行。
