# 0-build

## 确定本次交付

读取目标路径适用的项目指令、`docs/workflow.md` 或现有等效约定，再读取关联需求、任务及实现。按项目实际位置查找资料。明确的聊天需求可以直接实施，项目没有流程文件时沿用现有约定。UI 改动前读取项目根 `DESIGN.md`，缺失时按适用的项目或个人约定处理。变更适用的设计规范须已有明确授权。

从需求提取可观察的验收结果，定位相关入口、调用方及兼容约束。需要隔离既有改动或交接差异时，记录实施起点和任务涉及的文件。遇到会改变业务行为、范围或验收结果的未决选择时，保留已有行为，推进已明确且独立的部分，并提出需要决定的具体问题。

## 实施与排错

正式交付接入实际接口与数据；原型、测试替身及占位明确标识，交付时说明未接通部分。涉及接口或数据变更时，验证受影响的旧调用方、历史数据及方案要求的迁移和失败恢复路径。

按可验证的业务结果推进。多环节需求优先打通一条真实路径，再补相关边界。已有授权覆盖的步骤和验证入口直接使用。按项目要求或任务需要选择测试方式，适合时用先失败后通过的行为测试验证修复。

排查缺陷时，优先找能通过真实入口触发原症状的最小场景。原因不明时，用能区分候选原因的观察或实验缩小范围。性能问题用同条件下的前后测量判断。暂时无法复现时，记录可获得的证据、缺失的环境或输入，以及哪些结论尚待验证。修复后复测原场景，移除仅用于排查的临时改动。

## 验证与交付

用项目已有命令和受影响的入口核对验收结果及相关回归；多条互不干扰的验证命令可用 [run_checks.py](scripts/run_checks.py) 并发执行并获取带超时与尾部截断的摘要（`--help` 查看参数）。新增测试应覆盖现有验证遗漏的具体风险，或满足项目要求。按影响范围扩展检查，区分本次引入的失败、已有失败和环境受阻。适用时检查兼容输入、失败后的状态或 UI 实际交互。核对最终改动覆盖验收项，并能与既有改动区分。

同步本次变更影响的 README、模块说明、运行指引或其他现有文档。项目未指定位置时，长期认可的行为规格默认属于 `docs/specs`，复杂工作的任务记录默认属于 `docs/tasks`。仅按已认可的行为更新规格，遇到规格与实现冲突时记录差异和依据。已有任务记录按项目约定更新状态和验证证据，默认状态为计划中、进行中、受阻、已完成。小改按需更新已有文档。

交付时给出改动结果、位置、实际运行的验证及结果、有影响的未验证项和原因。自查按实际执行的检查报告，独立评审结论以独立评审实际完成为准。提交、推送、部署和外部任务状态变更按本次授权执行。
