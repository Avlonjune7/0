# 审查设计与代码

## 确定范围

先读项目适用的指令、`docs/workflow.md` 或实际工作约定。按用户指定的对象、版本和范围审查，记录目标和基线。以用户要求、已认可规格、关联 issue 或已记录决策为需求依据。规格缺失时，继续可证实的审查，并注明哪些要求无法判断。涉及 UI 方案或变更时，按项目约定读取根 `DESIGN.md`。

- **设计审查**：定位用户要审的规格、技术方案或实施计划及相关章节。对照已有需求、约束和决策，使用必要的实现或接口资料验证关键假设。文档本身应让目标读者理解目标、边界和决策。规格重点查遗漏、冲突、失败场景和可验收性。技术方案与实施计划还应查接口、依赖、兼容、迁移和验证方式中与本次任务有关的缺口。
- **代码审查**：按[确定 Git 比较范围](references/git-scope.md)区分已提交范围和工作区。沿变更追查真实入口、调用方和相关测试，核对需求遗漏、错误行为、超出授权的变更及回归。另据可定位的项目规范检查实现约定，按实际影响报告问题。

## 按风险独立复核

局部、低风险审查可直接完成。跨模块、高风险变更、复杂设计或用户要求独立审查时，选最需要独立判断的角度。单一风险通常交给一名审查者，能独立推进且各有证据的角度可并行。举例来说，设计可分别验证可理解性和实现可行性，代码可分别核查需求符合性和项目约定。

用无历史的新上下文启动只读子代理。在 Codex 使用 `fork_turns: "none"`。交给它范围、确定的基线、原始需求及证据路径、可用验证方式和交付要求，省略主会话推测、既有审查意见和拟定结论。无法派出独立审查，或审查者失败、超时、未提交结果时，完成可做的主会话审查，并标明对应复核未完成。

## 核实、报告与解决意见

主会话回到原文、实际调用路径和适用约定核实意见，合并重复项。每条发现给出位置、可检查的依据、触发条件或缺失场景、影响和建议。区分已证实的问题、尚待确认的假设与可选建议。按影响排序，说明关键证据或检查覆盖。无问题时写明已查范围及缺口。实际通过、失败和未运行的验证分别记录。

默认只读审查。本次任务已有修复授权时，核实后批量处理授权范围内且无需新决策的问题，并定向验证。对每条重要意见记录处置和依据，使用适用状态：待修复、修复并验证、证据推翻、经确认接受风险或待决策。质疑意见时引用可复查的反证。依据不足或涉及产品决策时保留该项及原因。复核新证据后更改严重程度时保留原判断和变更理由。

单轮审查在范围覆盖和意见核实完成后交付。修复后的复查聚焦改动及相邻风险，并重新定位相应版本和行号。需要更深入审查时，给出具体目标和有限轮次。到达目标、上限或缺少决定结论所需的证据时，报告剩余问题和审查限制。
