# 0-review

## 1. 确定范围

- 按 `AGENTS.md` 的指针读取约定，记录审查对象、版本和基线。
- 需求依据：用户要求、已批准规格（AC 编号）、关联 issue、决策日志。缺少规格时继续可证实的部分，注明哪些无法判断。
- **设计审查**：定位规格、技术方案或实施计划及相关章节。
- **代码审查**：按 [git-scope.md](references/git-scope.md) 区分已提交范围和工作区，用 [collect_changes.py](scripts/collect_changes.py) 收集改动清单（`--help` 查看参数）。

## 2. 派出金鱼

- 局部、低风险的审查可由主会话直接完成，并注明未做独立评审。其余派无会话历史的只读子代理（Codex 下用 `fork_turns: "none"`）。
- 只交给它：范围与基线、原始需求原文或规格路径、改动清单或文档路径、可用的验证命令。不给本会话推测、既有审查意见和拟定结论；给路径，不贴全文。
- 评审角度，每个角度最多 5 条发现，每条附位置、依据、触发条件和影响：

  | 对象 | 角度 A | 角度 B |
  | --- | --- | --- |
  | 规格 / 方案 | 可理解：无背景读者能否读懂目标、边界和决定 | 可实施：AC 可验证，与现有代码不冲突，步骤依赖完整 |
  | 代码 | 规格：逐条 AC 是否实现，有无越权改动 | 规范：项目约定、错误处理、兼容与回归 |

- 范围较大时两个角度各派一个子代理并行；范围小时合并给一个。
- 子代理失败、超时或没有结果时，完成主会话能做的部分，并标明哪个角度未复核。

## 3. 核实与报告

- 主会话逐条核对发现涉及的原文、调用路径和适用约定，合并重复项。只核实发现的证据，不重做全量审查；仍有效的验证结果直接复用。
- 分为已证实问题、待确认假设和可选建议，按影响排序。
- 报告格式（无问题时用一行写明已查范围）：

  ```text
  [严重|一般|建议] 位置：问题；触发条件；影响；建议
  覆盖：已查范围 / 未查范围
  验证：通过 / 失败 / 未运行
  ```

  不复述没有问题的部分。

## 4. 处置

- 默认只读。本次已授权修复时，批量修复证据成立且无需新决定的问题，并定向验证。
- 每条重要意见标明状态：待修复、已修复并验证、证据推翻、接受风险、待决定。反驳意见时附可复查的反证；调整严重程度时保留原判断和理由。
- 默认一轮。修复后的复查只看改动及相邻风险，并重新定位版本和行号。需要更深入审查时，给出具体目标和轮次上限。
