# 0-plan

交付有依据的规划结果。业务代码变更由实施阶段负责。

## 调查现状

先读适用的项目指令、`docs/workflow.md` 或项目实际采用的工作约定。沿用项目已有的说明、规格、架构、计划和记录位置。缺少约定时继续规划。涉及界面时先读项目根 `DESIGN.md` 并据此设计，缺失时按适用的项目或个人约定处理。根 `DESIGN.md` 用于 UI 规范，技术方案沿用项目的方案文档位置。

读取用户指定的材料、相关已认可要求与决策，再沿实际入口查明相关实现、调用方、数据约束与验证入口。用可定位的文件、符号或条款支持影响方案的事实。区分当前行为、认可要求和拟议变更。当前行为与认可要求有出入时，记录证据和方案影响，保留已认可要求。没有既有实现时，以已有材料为依据，标明需要验证的假设。

## 澄清与设计

- 明确目标、受影响场景、交付边界和约束。先查能从项目或已有讨论确定的事实。仍无法确定且会改变业务行为、范围、外部契约或重大成本时，向用户提出关键决策、影响和建议。先解决会决定后续问题的事项，同时完成独立部分。次要且可逆的取舍可写明假设继续。
- 结合现有结构提出方案，说明受影响的模块与行为。存在会影响选择的备选时，解释取舍。按实际影响说明接口、状态、兼容性、迁移或上线顺序。遇到与已确认决定的实质冲突，明确需要裁决的地方；待定方案保留为草案。
- 把需求写成可观察的验收条件，说明在什么前提下，哪些输入或操作应产生什么结果。覆盖与本次变更相关的正常和边界场景。优先在现有入口验证，写明验证方式及必要前置条件，并区分已查明的事实和实施后待执行的验证。
- 复杂任务按可独立验证的业务结果组织步骤，写明每步交付、验收方式和真实依赖。迁移等需要分阶段完成的工作按兼容顺序组织。规划可用一份记录表达，拆票取决于项目实际需要。

## 保存与交接

- 简短方案可直接交付于会话。需要持久记录时沿用用户指定位置或已有文档与工作约定，复用现有内容并保留已批准规格。无既有约定时，已认可的长期行为默认记入 `docs/specs/`，某次复杂工作的草案与步骤默认记入 `docs/tasks/`。待定方案标记为草案，修改长期规格以已有批准为依据。引用实际存在的文件，拟建位置用文字注明。
- 如需登记任务状态，沿用项目约定，默认可用「计划中」「进行中」「受阻」「已完成」。规划完成可以交接，任务状态按实际实施进度记录。远端 tracker 的写入按用户本次已有授权执行。
- 交接前对照已认可需求与适用约束，核对范围、验收条件、依赖和未决项。交付方案或文件位置、已确认决定，以及仍影响实施的前置条件。关键决策未定时，标明受影响的部分和已完成的独立部分。交接后结束本技能。同次已明确授权实施时，由主会话承接实施阶段。

方法参考 [Matt Pocock 的技能库](https://github.com/mattpocock/skills) 与 [Elephant–Goldfish Model](https://github.com/google/elephant-goldfish-model)。
