# 0-plan

产出可直接实施的已批准规格。不改业务代码。

## 1. 调查

- 按项目 `AGENTS.md` 的指针读取约定（通常是 `docs/workflow.md`、`docs/decisions.md`，涉及 UI 时读根 `DESIGN.md`）；没有约定就沿用现有结构。
- 互不依赖的读取和搜索并行发出。沿真实入口查到调用方、数据约束和验证命令即可停止。
- 影响方案的事实附文件或符号位置。分清当前行为、已认可要求和拟议变更；两者冲突时保留已认可要求并记录证据。

## 2. 澄清

- 能从代码或已有文档查到的不问。
- 会改变业务行为、范围、外部契约或明显成本的未决点：一次提 1–3 个，每个附推荐选项和影响。先问决定后续分支的，同时推进独立部分。次要且可逆的写明假设后继续。
- **深挖模式**：用户说"深挖"或"grill"时，一次只问一个问题并附推荐答案，逐个追问，直到决策树没有未决分支。

## 3. 写规格

按任务规模取舍，至少包含：

- **目标**：目标、非目标、交付边界。
- **方案**：受影响的模块与行为；存在影响选择的备选时写取舍；按实际涉及写接口、兼容、迁移和失败恢复。
- **验收条件**：编号 `AC-1`、`AC-2`…，每条写成"前提 + 操作 → 可观察结果"，覆盖正常和相关边界场景，注明验证方式。
- **步骤**：复杂任务按可独立运行、验证的纵向切片排列，每步写交付、对应 AC 和依赖（如 `依赖：步骤 2`）。
- **决定**：本次新做的关键决定追加到决策日志（位置和格式见项目 workflow）。

小任务的规格直接在会话中交付。需要持久化时沿用项目位置；没有约定时，长期行为写入 `docs/specs/`，某次工作的方案与步骤写入 `docs/tasks/`。文件头标明状态：`草案` 或 `已批准`。修改已批准规格需要用户同意。

## 4. 金鱼评审与批准

满足任一条件即执行：跨模块、改外部契约或数据、步骤不少于 3 步、用户要求评审。

1. 派一个无会话历史的只读子代理（Codex 下用 `fork_turns: "none"`），只给规格路径、原始需求原文和相关源码路径，不给本会话的推测和结论。
2. 要求它从两个角度各给最多 5 条发现，每条附位置和依据：
   - **可理解**：没有本会话背景的人能否读懂目标、边界和决定。
   - **可实施**：照规格能否直接动手并判断何时完成；AC 是否可验证，是否与现有代码冲突，步骤依赖是否完整。
3. 主会话逐条核实。证据成立的直接修订规格，涉及产品决定的交给用户。默认只评审一轮。
4. 请用户批准，批准后把状态改为 `已批准`。

无法派出子代理时，说明未做金鱼评审，由用户决定是否继续。完整的评审规则见 [0-review](../0-review/SKILL.md)。

## 交付（不超过 8 行）

规格位置或摘要、AC 数量、金鱼评审结果（已修订 / 待决定）、未决问题、下一步（`$0-build`）。本次已授权实施时，批准后直接按 0-build 继续。
