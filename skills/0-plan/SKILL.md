# 0-plan

产出可直接实施的已批准规格。不改业务代码。

## 1. 调查

- 按项目 `AGENTS.md` / `CLAUDE.md` 指针读取已有 `docs/workflow.md`、`docs/decisions.md`（涉及 UI 读根 `DESIGN.md`）；无约定沿用现状。
- 沿真实入口查到调用方、数据约束和验证命令即可停止；影响方案的事实附文件或符号位置。分清当前行为、已认可要求与拟议变更，冲突时保留已认可要求并记录证据。

## 2. 澄清

- 能从代码或已有文档查到的不问。
- 会改变业务行为、范围、外部契约或明显成本的未决点：一次提 1–3 个，每个附推荐选项和影响。先问决定后续分支的，同时推进独立部分。次要且可逆的写明假设后继续。
- **深挖模式**：用户说"深挖"或"grill"时，一次只问一个问题并附推荐答案，逐个追问，直到决策树没有未决分支。

## 3. 写规格

按任务规模取舍，至少包含：

- **目标**：目标、非目标、交付边界。
- **方案**：受影响的模块与行为；存在影响选择的备选时写取舍；按实际涉及写接口、兼容、迁移和失败恢复。
- **验收条件**：编号 `AC-1`、`AC-2`…，每条写成"前提 + 操作 → 可观察结果"，覆盖正常和相关边界场景，注明验证方式。
- **步骤**：复杂任务按可独立运行、验证的纵向切片排列，每步写交付、对应 AC 和依赖（如 `依赖：步骤 2`）。
- **决定**：本次新做的关键决定追加到决策日志（位置和格式见项目 workflow）。

小任务的规格直接在会话中交付。需要持久化时沿用项目位置；没有约定时，长期行为写入 `docs/specs/`，某次工作的方案与步骤写入 `docs/tasks/`。文件头标明状态：`草案` 或 `已批准`。修改已批准规格需要用户同意。

## 4. 金鱼评审与批准

- **触发条件**：跨模块、改外部契约或数据、步骤不少于 3 步，或用户要求评审。
- 按 [0-review](../0-review/SKILL.md) 的规格评审协议执行一轮金鱼评审：只传规格路径、原始需求原文和相关源码路径，不传本会话推测与结论。
- 主会话逐条核实：证据成立的直接修订规格，涉及产品决定的交给用户。若本轮存在 [严重] 问题且引发较大修订，对修订部分追加一轮定向金鱼复查。无法派出子代理时说明未做独立评审，由用户决定是否继续。
- 请用户批准，批准后把状态改为 `已批准`。

## 交付（不超过 8 行）

规格位置或摘要、AC 数量、金鱼评审结果（已修订 / 待决定）、未决问题、下一步（`$0-build`）。本次已授权实施时，批准后直接按 0-build 继续。
