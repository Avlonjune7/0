# 0-optimize

以整个工程完整源码为优化范围，从全局视角降低系统复杂度并提升执行效率与响应速度。默认先只读测绘与出方案，经用户确认后再改代码。

## 核心原则

1. **全局杠杆优先**：优先跨模块合并重复链路、删减无价值抽象层、消除架构级 I/O / 锁 / 序列化 / 重复计算瓶颈，不做逐文件微调。
2. **复杂度与性能取舍**：优先「既降复杂度又提性能」的改动；为换取性能增加复杂度时，必须证明处于实测热路径且收益显著，绝不为了刷分引入复杂 hack。
3. **行为与契约保护**：不静默破坏公共 API、数据格式、并发安全与既有业务语义；涉及契约变更时先单列待拍板项。
4. **同口径实测与免动区**：所有结论以改前/改后同口径实测数据为准，已达标的免动区明确锁定不改；无实测提升或引入回归的改动直接回退。

## 1. 全站测绘与双源基线（只读）

- 按项目 `AGENTS.md` / `CLAUDE.md` 读取 `docs/workflow.md`、`docs/decisions.md`，记录开工提交与 `git status`（若同文件已有未提交改动，按 `0-build` 规则保留基线差异）。
- 运行 [scripts/baseline_snapshot.py](scripts/baseline_snapshot.py)（可用 `--out` 保存改前 JSON）获取技术栈、代码体量、大文件热点、依赖数与本机可用性能工具快照。
- 按 [references/audit-profiles.md](references/audit-profiles.md) 启用适用的 **4 象限**（入口与前端体验 / 服务与数据链路 / 工程与交付效率 / 架构与复杂度健康度；不适用标 `N/A`），采集双场景实测基线（如前端 Desktop vs Mobile 节流、后端常规 vs 压力/冷启动；Web 禁测 dev server）。

## 2. PSI 式诊断与方案拍板（门禁）

- 顶部输出 **4 象限红/黄/绿体检总览卡**。
- 诊断严格分三段：**Opportunities（量化预估收益：省多少 ms / MB / 查询数 / 行数，按收益降序）** → **Diagnostics（架构与复杂度根因）** → **Passed（已达标免动区，明确不改）**。
- 按「收益 / 风险 / 改动面」组织 Top N 原子批次（目标、涉及模块与调用方、`AC-1`…、回滚方式）；先用大白话列出业务影响与待拍板项，技术细节后置。
- 跨 3 个及以上模块或高风险重构，按 `0-review` 规格评审协议派金鱼子代理独立复核方案；获用户批准后再动手。

## 3. 分批原子实施

- 按依赖从底层/边界向上层分批落地，每批保持独立可编译、测试全绿、可单独回滚；严禁一次性铺开改几十个文件。
- 每批完成后立即跑回归测试与定向基准，达标后再进下一批；未达预期则定位根因或回退该批。
- 实施中发现的新全局问题记入后续清单，不顺手扩范围。

## 4. 同口径复测、金鱼评审与交付

- 用同一组测试/基准命令和 `baseline_snapshot.py --compare <before.json>` 复跑，输出**改前 vs 改后 4 象限对比卡**（已安装 `0-build` 时多条互不干扰命令可用其 `run_checks.py`）。
- 按 `0-review` 代码评审协议做一轮金鱼评审（已安装 `0-review` 时优先用其 `collect_changes.py`，否则用 `git diff` 收集改动），修复证据成立的问题并定向复测。
- 同步受影响的 README、模块说明，关键架构取舍追加到 `docs/decisions.md`。
- 交付不超过 12 行：优化范围与批次、改前/改后关键指标对比、测试与金鱼评审结果、遗留缺口与回退说明。
