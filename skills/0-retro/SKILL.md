# 0-retro

关注工作过程、工具和项目约定怎样影响结果。代码或设计的独立审查由 `0-review` 负责，换窗口接续由 `0-handoff` 负责；本技能不自动调用它们。

## 确定事实

用户指定的会话或任务优先，未指定时复盘当前会话。复用可见记录，按需读取关联任务、变更、命令输出和项目配置；需要历史记录时，仅定位指定会话，不遍历无关聊天。记录不可访问或上下文已缺失时，说明覆盖范围，不根据最终代码虚构开发过程。

找出实际发生的返工、重复调查、错误判断、遗漏检查或信息缺口，记录触发场景、证据位置和影响。区分已证实原因与待验证推测，不把耗时或失败本身当作代理失误。已有验证仍适用时不重跑；若需要新实验确认原因，先判断是否属于现有授权。

## 选择最小改进

只检查与已发现问题有关的方向，不为填满分类制造发现：

- **导航与依赖**：反复定位或漏掉关键依赖时，核对已有 README 和入口指引，优先修正缺失或误导的指针。
- **自动检查**：先查项目已有命令、测试、lint、类型检查及 CI。区分没有检查、检查失效和已有检查未运行；能稳定判定的重复错误优先复用或补充确定性检查，而非追加提醒。
- **判断与规则**：需要跨文件或业务判断的问题，在已有适用文档中澄清。单次失误不足以推导全局规则；先检查是否已有有效规则以及未遵守的原因。
- **工具与上下文**：依据实际调用记录识别重复读取、过量输出、重复验证或无效交接；建议复用结果、缩小范围或批量处理。没有测量时不编造 token、耗时和节省比例。
- **信息获取**：日志或必要事实缺失时，指出最小的信息入口及权限需求；不据此自行扩权、暴露凭据或接入服务。

比较改进的预期收益、维护成本和适用范围。优先项目内已有机制；没有 CI、hook 或专门规范文件本身不构成必须新增它们的理由。不为一次性工作增加脚本，也不为复盘默认创建新的规范体系。

## 交付与实施边界

默认在会话中给出少量高价值建议，按实际影响排序。每项说明 **问题证据 → 原因或待确认点 → 最小改进及位置 → 验证方式**。不要求固定数量；没有充分依据时明确表示暂不建议改动。已解决的问题只在仍有可复用教训时保留。

复盘请求本身不授权修改项目、技能、全局规则、记忆或配置。当前任务已有明确改进授权时，实施对应范围内无需新决策的修改，并定向验证；其余维持建议状态。区分建议、已实施、已验证和仍有缺口，不能把建议写成已经完成。

仅在用户要求保存报告时，沿用指定位置或已有任务记录；引用已有材料，保留人工说明，不重复复制整个会话。报告排除凭据和无关个人信息。

交付有依据的建议与实际实施结果后停止，不自动开始下一轮开发、审查或复盘。

方法参考 Matt Pocock 的 retro，按 0 工作流的按需改进与手动触发约定适配。
