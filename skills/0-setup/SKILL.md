# 0-setup

让后续开发者或代理能找到运行入口、理解模块边界、定位规格和任务，并保持项目文档与源码一致。默认使用简体中文，沿用项目已有语言要求。

## 范围与模式

- 输入为项目或子目录路径及用户给出的文档要求；未给路径时使用当前工作目录，目标不明确时先定位，不从无关历史推定项目。
- 区分三种模式，默认**轻量接入**：
  - **轻量接入（默认）**：复用或按需接入本地 Git，建立或补齐 `AGENTS.md`、`docs/workflow.md`、根 `README` 及必要入口导航；只读配置、入口、契约与已有文档，按需最少读取，避免初始化阶段全量扫源码。
  - **深度建档（按需）**：仅在用户明确要求全库模块建档，或接手缺少说明的大中型代码库且需生成分层模块 README 时启用，覆盖范围内第一方源码并自底向上逐层写文档。
  - **漂移核对与同步（按需）**：仅在用户要求集中检查文档漂移或同步过期实现说明时启用；直接按 [doc-sync.md](references/doc-sync.md) 执行，无需重跑完整初始化或 Git 接入。
- 完整项目初始化包括建立或复用本地 Git、补齐必要忽略规则和项目文档；远端按已有授权接入。局部或明确仅文档任务保持原范围。业务代码、依赖、提交、推送和部署不属于默认动作。
- 说明本次文档范围后，常规可逆写入直接完成；只对无法查明的重要选择、真实规则冲突或超出范围的操作询问。
- 参考 Matt Setup 的低摩擦接入约定，以及 EGM Bootstrap / Drift Report 的模块建档与文档核对方法；无需安装或调用它们。

## 1. 识别现状

优先调用 [scan_project.py](scripts/scan_project.py)（`--help` 查看参数）列出已有文档、常见配置与候选源码目录，再按 [discovery.md](references/discovery.md) 核对当前目录、适用指令、已有改动与项目入口。

- 仅在完整初始化且缺少本地 Git、仓库边界存疑或用户要求接入远端时，再读取 [git-setup.md](references/git-setup.md) 处理版本管理；已有仓库和 worktree 直接复用。
- 建立简短工作清单：本次模式（轻量接入 / 深度建档）、需补齐的文档、复用的权威来源、需读取的入口或模块、尚不能确认的事实。已有规格、计划、架构或 tracker 约定优先复用，不为套默认目录改名或搬迁。

完成条件：分清新项目、已有代码库或局部目录及本次模式；每份拟写文档有实际职责，不与已有文档重复。

## 2. 明确项目约定

默认布局如下，仅创建有内容的文件；涉及文档职责细节、模块文档写法或 UI `DESIGN.md` 规则时，按需读取 [documentation.md](references/documentation.md) 对应章节：

```text
project/
├── AGENTS.md                 # 项目约束和按需读取入口
├── README.md                 # 介绍、运行入口、模块导航
├── DESIGN.md                 # 项目唯一 UI 规范，无 UI 不创建
├── docs/
│   ├── workflow.md           # 文档职责、位置、读取和更新约定
│   ├── specs/                # 有实际功能规格时再建
│   └── tasks/                # 有实际复杂任务时再建
└── 实际代码目录/
    └── 实际模块/README.md    # 仅深度建档或复杂模块需要时创建
```

代码目录沿用现状，不创建示例 src 或 module-a。已有 AGENTS.md / CLAUDE.md 按现有分工维护；仅有 CLAUDE.md 时复用它，不另造冲突规则；两者均不存在时默认创建 AGENTS.md。

用 [workflow 模板](assets/workflow.md) 记录后续技能可消费的约定：规格与任务的实际位置、tracker、状态表示、文档的读取与更新时机。没有既有 tracker 时默认本地 Markdown；存在 GitHub remote 并不等于项目使用 GitHub Issues。尚未创建的目录写为约定路径，不生成虚假链接。

完成条件：每类信息有一个权威位置，未创建的文档与已存在文档可区分。

## 3. 建立事实依据

- **轻量接入（默认）**：读取构建/运行配置、主入口、对外契约、验证命令与已有文档；只写已核实的入口与边界，不推测未读实现细节，后续开发按需再读对应模块。
- **深度建档（按需）**：完整阅读将要描述的第一方模块实现、接口、Schema 与验证入口，已有 README 须对照当前源码核实；模块边界依据代码职责与依赖确定，小项目根 README 足够时不拆模块文档。范围内源码总量 ≤ 1,500–2,000 行或仅 1 个逻辑块时由主会话直接完整读取；超过单块阈值时按 [deep-scan.md](references/deep-scan.md) 分块并发调度只读子代理，主会话汇总后再由叶子向根逐层写文档。
- 读取受限、依赖缺失或调查失败时，继续独立部分并将对应范围标记为未完成，不用占位内容宣称已覆盖。
- **空项目**：只记录用户已确认的目标和实际已有信息；缺少关键用途时询问，不虚构技术栈、接口、命令、模块或实现进度。

完成条件：拟写事实可追溯到对应配置或源码，推断、已认可要求、当前行为与未覆盖范围已区分。

## 4. 写入文档

按职责只创建或更新必要文档；需要生成模块文档时参考 [模块模板](assets/module-readme.md)，删除不适用章节与写作提示，不为每个目录机械生成 README。

- 保留人工说明、已确认决策和无关内容；原地修改相关章节，不整份覆盖。已有模块说明名称和位置优先复用。
- 发现已确认规则与代码不一致，记录差异及证据，不自行改成“代码当前行为就是正确要求”。
- 文档只记录变量名、用途和配置来源，不复制真实凭据或运行时敏感数据。
- 本阶段不撰写新的产品需求或开发任务，不创建空 specs、tasks、术语表或 ADR。

完成条件：文档描述实际项目；入口链接可导航到本次生成或已有的有效文档。

## 5. 核对并交付

逐份阅读本次新建或修改的文档，核对：

1. 所述职责、接口、命令和边界可追溯到实际配置或实现，没有超出本次调查范围。
2. 所有本地链接目标存在（可用 [check_links.py](scripts/check_links.py) 批量核验）；规格和任务的未来目录只作为路径约定。没有遗留模板说明、虚构命令或重复规则区块。
3. 验证命令来自项目真实脚本或配置；区分“配置中存在”与“实际运行通过”。不为纯文档改动启动服务、执行迁移或跑全套业务测试。
4. 查看本次 diff 或文件变化，确认改动限于文档及约定的 Git 初始化、忽略规则，未覆盖其他会话的无关内容。项目未变化时，再次运行应保留有效文件，不刷新时间戳制造修改。

最终简述：本次采用的模式、生成或更新了什么、覆盖范围与如何核对、仍有哪些缺口。相关工作完成即停止，不自动进入规划、开发或另一轮漂移审查。
