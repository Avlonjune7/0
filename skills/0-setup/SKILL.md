# 0-setup

让后续开发者或代理能找到运行入口、理解模块、定位规格和任务，并知道何时读取与更新文档。默认使用简体中文，沿用项目已有语言要求。

## 范围

- 输入为项目或子目录路径及用户给出的文档要求；未给路径时使用当前工作目录，目标不明确时先定位，不从无关历史推定项目。
- 完整项目初始化包括建立或复用本地 Git、补齐必要忽略规则和项目文档；远端按已有授权接入。局部或明确仅文档任务保持原范围。业务代码、依赖、提交、推送和部署不属于默认动作。
- 使用当前用户授权和项目规则。说明本次文档范围后，常规可逆写入直接完成；只对无法查明的重要选择、真实规则冲突或超出范围的操作询问。
- 参考 Matt Setup 的项目接入约定与 EGM Bootstrap 的源码文档方法；无需安装或调用它们，不继承它们的确认次数或文件模板；源码阅读按本技能规定的分块与并发要求执行。

## 1. 识别现状

读取 [discovery.md](references/discovery.md)，核对当前目录、适用指令、已有改动、项目入口及文档。

完整项目初始化先按 discovery.md 的“Git 接入”确保本地版本管理可用，区分仅本地仓库与已验证的远端；已有仓库和 worktree 优先复用。

建立简短工作清单：需要补齐的文档、复用的权威来源、需要读取的模块、尚不能确认的事实。已有规格、计划、架构或 tracker 约定优先复用，不为套默认目录改名或搬迁。

完成条件：分清新项目、已有代码库或局部目录；每份拟写文档有实际职责，没有与已有文档重复的来源。

## 2. 明确项目约定

读取 [documentation.md](references/documentation.md)。默认布局如下，仅创建有内容的文件：

```text
project/
├── AGENTS.md                 # 项目约束和按需读取入口
├── README.md                 # 介绍、运行入口、模块导航
├── DESIGN.md                 # 项目唯一 UI 规范，按适用范围处理
├── docs/
│   ├── workflow.md           # 文档职责、位置、读取和更新约定
│   ├── specs/                # 有实际功能规格时再建
│   └── tasks/                # 有实际复杂任务时再建
└── 实际代码目录/
    └── 实际模块/README.md    # 模块职责、接口、约束、依赖、验证入口
```

代码目录沿用现状，不创建示例 src 或 module-a。已有 AGENTS.md / CLAUDE.md 按现有分工维护；仅有 CLAUDE.md 时复用它，不另造冲突规则。两者均不存在时默认创建 AGENTS.md。

用 [workflow 模板](assets/workflow.md) 记录后续技能可消费的约定：规格与任务的实际位置、tracker、状态表示、文档的读取与更新时机。没有既有 tracker 时默认本地 Markdown；存在 GitHub remote 并不等于项目使用 GitHub Issues。尚未创建的目录写为约定路径，不生成虚假链接。

完成条件：每类信息有一个权威位置，未创建的文档与已存在文档可区分。

## 3. 建立事实依据

- 已有项目：按工作清单完整阅读将要描述的第一方模块实现，以及相关配置、接口、Schema 和验证入口；调用链中的关键约束需追踪到实际维护它的实现。测试可用于理解行为，不因目录名为 tests 就统一忽略。
- 模块边界依据代码职责、包入口和依赖关系确定，不机械地每个目录都生成 README。小项目根 README 足够时，不拆模块文档。
- 必须按 discovery.md 的“分块与独立并发阅读”执行：以完整函数、类或方法边界分块，每块目标约 1,500 行；用无会话历史的只读子代理读取，有多个可独立块时并发，按全局约定与宿主实际可用额度中的较低上限调度，其余排队。子代理能力不足时明确记录限制，不静默改成主会话代读并宣称完成。
- 已有 README 也必须重新核对本次范围内的当前源码；旧说明只能作为待核对材料，不能代替实际读取。主会话先汇总并核实模块事实，再由叶子模块向父模块、项目根目录逐层写文档。
- 读取受限、依赖缺失或调查失败时，继续独立部分，但将该模块标记为未完成；不能用占位内容宣称已覆盖。
- 空项目：只记录用户已确认的目标和实际已有信息。缺少关键用途时询问；不虚构技术栈、接口、命令、模块或实现进度。

完成条件：本次范围内的源码分块均有已读取报告或明确未完成原因；拟写事实可追溯到对应源码，推断、产品要求与当前行为已区分。

## 4. 写入文档

按 documentation.md 的职责和更新规则，先完成已核实叶子模块的说明，再汇总子模块事实写父级与根入口；只创建有实际职责的文档，不为每个目录机械生成 README。建立工作约定及必要模块说明。模块内容参考 [模块模板](assets/module-readme.md)，删除不适用章节与写作提示。

- 保留人工说明、已确认决策和无关内容；原地修改相关章节，不整份覆盖。已有模块说明名称和位置优先复用。
- 发现已确认规则与代码不一致，记录差异及证据，不自行改成“代码当前行为就是正确要求”。
- 文档只记录变量名、用途和配置来源，不复制真实凭据或运行时敏感数据。
- 本阶段不撰写新的产品需求或开发任务，不创建空 specs、tasks、术语表或 ADR。

完成条件：文档描述实际项目；入口链接可导航到本次生成或已有的有效文档。

## 5. 核对并交付

逐份阅读本次新建或修改的文档，核对：

1. 模块职责、接口、状态和副作用可追溯到实际实现，文档没有超出调查范围。
2. 所有本地链接目标存在；规格和任务的未来目录只作为路径约定。没有遗留模板说明、虚构命令或重复规则区块。
3. 验证命令来自项目真实脚本或配置；区分“配置中存在”与“实际运行通过”。必要时运行不会产生额外副作用的文档检查，不为纯文档改动启动服务、执行迁移或跑全套业务测试。
4. 查看本次 diff 或文件变化，确认改动限于文档及约定的 Git 初始化、忽略规则，未覆盖其他会话的无关内容。核对仓库根路径与状态；新仓库尚无提交时如实说明。远端接入以实际验证结果交付。项目未变化时，再次运行应保留有效文件，不刷新时间戳制造修改。

最终简述：生成或更新了什么、覆盖哪些模块、如何核对、仍有哪些缺口。相关工作完成即停止，不自动进入规划、开发或另一轮漂移审查。发现部分失败时如实报告部分完成。
